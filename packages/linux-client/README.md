# `@nanosync/linux-client` — Linux filesystem adapter

This package scans and watches a Linux sync directory and safely materializes authenticated remote manifests and files. It builds on `sync-core` and `client-local`; the daemon and CLI now provide the continuous operation and user command surfaces.

## Step 13 materialization boundary

`applyNewFiles(root, local, remote, authenticatedManifest, acceptedSequence, master, { evictIds? })` authenticates the remote manifest and stages **all** required file downloads in private 0600 (0700 executable) temporary files inside the root before mutating local data. Each bounded chunk is verified by `downloadChunks`, and the streamed file length/SHA-256 is checked before fsync. It inventories and verifies local owner, inode, hardlink count and whole-file digest against persisted identities; unknown entries, symlinks, special files and edits fail without turning into deletions. It persists a secret-free apply plan (old inode/fingerprint, target manifest, staged names, selected eviction) before the first mutation. Files and directories are extracted to uniquely named temporary entries and reassembled by stable ID, supporting nested creation, replacement, rename/move, tombstones and explicit eviction. Installed new files use an atomic no-replace hard link. `evictIds` requires the accepted authenticated head and presence of every referenced remote chunk; omitted remote-only files retain their namespace without hydration. Fsync precedes a single database transaction that commits identities, suppression and applied head. Replay the **same** accepted manifest/sequence after reopening to resume a pending intent; never run a scanner while a pending intent exists.

**Operational limits:** The root is not a transaction: a crash after extraction can temporarily leave paths absent until replay completes. On replay, old descendants beneath one or more staged parent directories are matched by their persisted inode/content identity; unexpected children are rejected. An interrupted apply needs access to the same master key and remote revision to authenticate and possibly re-download staged files; a missing or conflicting source/stage fails visibly instead of silently deleting user work. A hostile same-UID concurrent writer may rename a parent directory between the fd-based checks and a filesystem call; Node cannot provide a fully race-free `openat2`/`renameat2` transaction or atomic no-replace directory rename. The implementation checks root/parent/leaf identity before and after each operation and refuses observed conflicts, but **do not use it on concurrently adversarial filesystem trees**. The daemon/CLI serialize normal operations, resolve interrupted intents before scanning, and surface blocked intents for operator intervention. Eviction selection is command-driven rather than automatic. Downloads are sequential with one 4 MiB chunk plus its transport frame in memory; disk staging capacity must accommodate all pending files.

`LinuxScanner.plan(priorManifest, revisionId, deviceId, master)` returns a validated manifest and a repeatable `chunks(knownObjectIds?)` async generator. Pass the manifest, sorted authenticated prior references (including evicted files), and `plan.chunks(new Set(knownReferences.map(r => r.objectId)))` to the Step 9 publisher. Only supply prior references actually required by the new manifest. If a remote-known reference needs repair, omit it from the set and supply its verified frame instead. Frames are encrypted in natural manifest file/chunk order on demand; no 50 GB buffer or spool is held. Do **not** commit the plan until publication/application succeeds. A failed publication needs a new plan/revision, and an unresolved frozen proposal must be resolved before retrying.

`LinuxWatcher.start()` watches known directories; call `ready()` periodically, and on `true` run `plan()` and `start()` again to refresh watches. Events, overflow, startup, and restart all cause a **full** scan; event names are never trusted for deletions. `notify()` supports external watchers. Defaults: 250 ms quiet debounce, then two identical metadata snapshots at least 500 ms apart; 256-event batch overflow; two scan workers (maximum eight). `ready()` is intentionally pollable with an injected clock. This keeps incomplete editor saves out of a batch; streaming additionally verifies dev/inode, size, mtime, ctime and mode before/after each file. Stable snapshot is a heuristic, not a filesystem transaction: changes during a multi-file publish must be handled by another scan.

The ordinary-data root must be owned by the current user, not a symlink, and contain only owner-owned regular files and directories. Symlinks, hardlinks, special files, ambiguous case names, unsafe/NFD names, and files larger than 50,000,000,000 bytes fail the batch. Scan errors are not interpreted as deletion. Keep the private `ClientLocal` directory **outside** the data root. `recordScan` stores filesystem IDs for subsequent rename detection; the caller must commit only after successful reconciliation. The result reports consumed suppression matches so the daemon can avoid echoing an applied remote change.

Delete/recreate assigns a new live ID. If an old tombstone occupies the name, it keeps its ID but is renamed deterministically to a bounded ` (deleted <full UUID>)` archival name; deleted parent directories' tombstones are moved to the nearest surviving directory (or root). Exhausted archival names fail visibly. Evicted live entries retain their namespace; a new local object at the same path is an explicit collision requiring reconciliation, never an inferred resurrection or deletion.
