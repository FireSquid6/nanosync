# `@nanosync/sync-core` — portable sync and cryptography

This package contains the portable client engine: v1 encrypted object/manifest handling, authenticated remote operations, history and restore planning, and shared synchronization interfaces. It depends on the protocol package and Web Crypto/WHATWG streams; platform persistence and filesystem access are adapters.

`HttpRemote.manifest(id, master)` verifies the revision reference-set MAC before downloading the manifest frame and calls `decryptManifest` to bind its plaintext to the envelope. `history(remote, head, master, path?)` traverses authenticated parent revisions and lists matching entries; `planRestore(current, historical, path, newRevisionId, deviceId, acceptedRevisionId)` builds a **new** revision parented to the caller's accepted current manifest, preserving the current file ID when replacing a live file. If a tombstone occupies the path, it retains its ID under a bounded, collision-checked archival ` (deleted <id>)` name and the restored file receives a fresh ID. `restoreReferences(planned, [{ manifest, envelope }], master)` verifies each source envelope MAC and exact reference set before returning sorted chunk references for publication. Re-check that `current` is still the accepted head at publication using the server CAS; these helpers do not perform publication. Directory/subtree restores remain outstanding; the shipped CLI supports whole-revision and historical single-file restore.

Runtime imports use only `@nanosync/protocol`, Web Crypto, and WHATWG streams. The caller retains the recovery secret and master key; neither is sent to the server. `EncryptedObject.reference` is server-visible frame metadata (its checksum covers the complete frame). File transforms yield one bounded 4 MiB chunk at a time; empty input yields no chunks. The source should produce bounded segments too.

**AAD interoperability:** The exact JSON field names and JCS ordering are frozen in `docs/security.md` and `docs/formats.md`: object AAD uses `cryptoFormatVersion`, `label`, `objectFormatVersion`, `objectId`, `objectType`, `plaintextLength`, `vaultId`, and recovery-wrap AAD uses `algorithm`, `label`, `vaultId`, `version`. For chunks, `objectId` is the keyed chunk ID. These schemas contain only ASCII strings and safe integers, so sorting keys and JSON-encoding values produces JCS. The reference-set MAC uses the protocol-validated envelope without `referenceSetMac`, in JCS order. Fixed vectors in `tests/crypto.test.ts` freeze the byte representation.

Web Crypto has no streaming GCM verification. This implementation deliberately caps individual randomized objects at 4 MiB (below the protocol's 64 GiB *maximum*) and rejects larger objects rather than releasing unauthenticated plaintext or buffering an unbounded frame. Large randomized objects require bounded authenticated temporary storage and a streaming crypto backend. Deterministic chunk encryption requires independent cryptographic review before production, as required by `docs/security.md`.

`encryptManifest`, `decryptManifest`, `encodeManifest`, `decodeManifest`, and `validateManifestReferences` implement the closed v1 tree schema in `docs/formats.md`. Encrypt the manifest first, then add its returned reference and all distinct chunk references to the envelope and compute its reference-set MAC. On read, `decryptManifest` validates the MAC before decrypting, then checks revision identity, tree, canonical bytes, and exact chunk membership. The caller must still verify whole-file SHA-256 when reconstructing files; the server cannot validate encrypted manifest plaintext.

`HttpRemote` accepts an injected fetch-compatible transport, server URL and bearer token. Call `capabilities()` before work (other methods negotiate lazily). `publish(manifest, knownReferences, newChunks, master, expectedRevisionId, createdAt)` takes sorted, unique **authenticated references from a previously verified manifest/envelope** for unchanged or remote-only chunks and an iterable/async iterable of distinct new encrypted frames **in any order**, including file order. Together they must match every distinct live chunk in the new manifest exactly, including type and complete frame length. The client checks remote presence of reused references in batches of at most 1,000; missing reused chunks must have a supplied verified frame for repair or publication fails without advancing head. New frames are checksum-, header-, AEAD- and keyed-ID-verified against the master key before upload. Presence queries for new frames use at most 16 bounded frames per batch; only missing frames are uploaded. Only compact reference metadata is sorted for the envelope. Then the client encrypts the manifest, authenticates the public reference set and advances the expected head. No whole-file plaintext or ciphertext is held in memory. It returns `staleHead` for the caller's later merge logic without changing the proposal. Transport retries within one call reuse the same envelope and head idempotency key; **a caller restarting `publish` after a process crash must persist its encrypted manifest/proposal to replay the exact request**, rather than re-encrypting a new randomized manifest. PUT retries reuse a per-attempt key, while a later repair gets a fresh key so a previously accepted idempotency replay cannot suppress the repair body. Servers advertising fewer than 32 idempotency-key characters are rejected: the truncated hexadecimal keys would otherwise carry fewer than 128 collision-resistant bits. `downloadChunks` accepts a `ChunkJournal` whose `put` durably commits authenticated plaintext and whose `get` retrieves it using the vault ID and full reference as the key; cached bytes are reauthenticated before skipping network reads. No default persistent journal is supplied.

The wire API requires an exact `Content-Length` on streamed PUT bodies. Browsers generally prohibit setting this header manually, so a browser transport must provide an approved upload bridge that can set the length; ordinary browser `fetch` cannot upload to this server as-is. This package itself has no Node runtime imports. Randomized frames larger than the bounded Web Crypto limit are rejected, not buffered.
